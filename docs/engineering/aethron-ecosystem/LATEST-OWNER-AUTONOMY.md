# Latest owner directive — continuous autonomy, integration and public delivery

**Issued 2026-10-08 after Phase 1 start. This directive supersedes previous requirements to stop at every numbered phase or ask for individual routine merge, release or GitHub Pages deployment approvals.** The owner clarified that work should proceed as one autonomous delivery process, without prompting them at each stage. The original Phase 1 start and Phase 0 planning remain valid history.

## Default operational intent

**CONTINUE AUTONOMOUSLY** through P1.1–P1.7 and subsequently the full software/research/packaging/SDK scope of P2–P5 as far as executable without physical device access, using implementation-first work with checkpoints; then integrate qualified changes with current upstream and publish approved software/web artifacts. No more owner START required merely because P1 becomes P2, P2 becomes P3, etc. No “may I commit/merge/push/deploy?” confirmations for routine software delivery. Proceed when objectively verified gates pass and safe access/credentials already exist.

- Complete one cohesive task, test it, record evidence, commit it on your assigned feature branch, then advance to the next executable task. Keep a machine-readable progress record, covered and pending hardware tuples, blocked reasons and current HEAD; do not manufacture completion.
- Maintain clean Git integration: fetch current main, detect other agents' active branches/worktrees, reconcile merges without clobbering. If CI fails, **diagnose and fix** and re-run the exact failed tests instead of asking the owner to approve bypass. If blocked by a platform or third-party right, continue on independent tasks and state exactly what is blocked.
- Once the cohesive deliverable is demonstrably ready, with full tests, security/privacy/license checks, no unresolved critical release blockers and no conflicting native-iOS changes, **routine GitHub PR, push/merge and deployment are authorized**. Use existing protected-branch/required-check workflows. Do not force-push, circumvent required checks, erase audit history, bypass a branch protection rule, or label known failures success. Use normal signed/verified credentials, respect GitHub controls.
- For web/site and documents, publish via existing public AETHRON repository and GitHub Pages deploy workflow automatically after green validation; prefer repeatable CI/CD, not manual one-off public state changes. For installable edge and native packages, prepare publishable signed candidates, manifests, release notes and reproducible evidence, then publish artifacts when repository requirements, signing capability, rights and release prerequisites are actually met. Do not claim a package is installable when not tested.
- Deployed **live perception on actual cars/drones/household cameras** is a different claim from GitHub Pages being live. Remote deployment to third-party vehicles/UAS, activation of motor/flight control, invasive access to factory cameras, actual physical retrofit or certification cannot be automated merely from this approval. Keep physical hardware/product-safety requirements distinct, and never issue actuation commands.
- Treat **consumer local appliance runtime** as the actual product: one-time provisioning, automatic supervised boot, local sensor handling/inference/events, no permanent attached developer laptop/phone/USB tether, WAN, Supabase/Coolify or online licence server. Preserve fallbacks/UNKNOWN when evidence is stale. No invented zero-visible sensing or field performance.
- Preserve current main's **GPL-3.0-only community licence + separate commercial licensing controlled by the owner**, public plans/pricing/Founding terms, unmodified third-party licences, accurate copyright chain, latest corrected official logo, public Pages routes and native iOS worktree. Do not use commercial requirements as a network activation gate.
- No third-party payments, paid resource procurement, deleting other teams' worktrees, disabling GitHub security, changing customer data, public marketing claims of safety certification or changing vendor API credentials. Materially new regulatory/safety-risk permissions need evidence and authorized human operation, not automatic software deployment.
- The numbered phases are **progress milestones**, not approval stops. When hardware or legal evidence is missing, implement and test software against virtual/replay/SITL where possible; mark exact SKU/real-world qualification pending, and continue other tasks. Never falsely declare the entire project “done” because a checklist passed.
- Keep runtimes detached and resumable across context/CLI turns: after each Codex run completes, the autonomy runner should inspect results and resume the **same thread** if executable work remains. Stop and report only when no safe executable work remains, an actual credential/permission blocker cannot be solved without owner action, or all agreed software/CI/publication outcomes have been evidenced.
- Prefer concise periodic status files with completed commit hashes, demonstrated capabilities, CI results and true blockers instead of requests for routine go-ahead.

**Scope of this autonomy is software implementation and validated releases/publication, not deployment or operational certification of safety-critical autonomous vehicle/drone functions.** This is owner-requested automation and does not erase the project's existing safety policy, frozen technical evidence or need for real hardware qualification.
