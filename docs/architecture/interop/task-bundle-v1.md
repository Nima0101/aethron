# Offline task bundle binding v1

A pinned task description alone does not bind the bytes supplied for verification.
`verify_task_bundle` closes that gap: validate the task, match every exact input digest,
enforce its evidence budget, and invoke passport/evidence verification again with the
caller's current trusted time, policy revision floor and software subject digest.

## Technology selection

Requirements: offline synchronous Linux/macOS/Windows software, immutable snapshots,
bounded work before parsing/hashing, no filesystem or network access, no scheduler,
retained failed/unknown evidence, no motion/execution authority. Task, envelope and
policy each have a 64 KiB ceiling; 0–16 evidence blobs each have a 64 KiB ceiling.
Maximum input bytes are therefore 1,245,184, before the task's tighter evidence budget.
No hard real-time or device-memory qualification is claimed.

Compare [Protobuf](https://protobuf.dev/programming-guides/encoding/) generated byte
containers, [FlatBuffers](https://flatbuffers.dev/white_paper/) direct buffer access,
and explicit immutable byte snapshots. Binary containers suit large structured message
transport, but neither authenticates referenced content and neither is needed to wrap
already-canonical signed bytes in this local API. Select the snapshot contract; future
network framing needs a separate profile and admission check.

For implementation consider Rust ownership with immutable borrowing, Java/Kotlin or C#
managed byte containers, Node buffers, and Python exact `bytes`/`tuple`. Rust's
[borrowing rules](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)
are attractive for native zero-copy consumers. Mutable managed buffers require ownership
or copying before concurrent access; [Python bytes](https://docs.python.org/3/library/stdtypes.html#bytes-objects)
provide immutability directly. Choose Python for this bounded adapter: immutable inputs
remain identical across digest checks and the native cryptographic calls, and composition
through the versioned public verifiers avoids a second trust-policy implementation.
The existing bounded hash probe and new negative contract tests evidence this choice;
no language speed ranking, installed-tool preference or rewrite-cost argument is used.

## API and rejection rules

`verify_task_bundle(task, envelope, policy, evidence, *, expected_task_sha256,
expected_subject_sha256, now_s, minimum_time_s, minimum_policy_revision)` takes exact
bytes and an exact tuple of exact bytes. Mutable buffers/subclasses, excess blobs and
oversize parts reject before hashing, JSON parsing or cryptographic verification.
Task pins must come from an authenticated external source. These APIs never fetch pins.

After task validation, envelope and policy SHA-256 must match their task pins. Evidence
must fit `max_evidence_bytes` and match the entire declared digest set without duplicates.
For `passport.verify.v1`, evidence must be empty. For `evidence.bind.v1`, the task's set,
actual byte set and signed passport reference set must all match. Reordering supplied
blobs is harmless; omitting failed evidence, adding content or substituting bytes rejects.

The adapter rechecks current trust on every invocation. Output expiry is the minimum of
task, passport and policy expiry. Results contain only digests, expiry, policy revision
and immutable signed evidence metadata; raw content is never returned. Outcomes remain
issuer assertions. `execution_authority`, `motion_authority` and `evidence_verified`
are always false, including serialized results. There is no cache, replay store,
resource reservation, remote transport or actuation path.
